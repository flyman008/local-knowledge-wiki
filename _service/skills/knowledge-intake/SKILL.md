# 知识库入库（Knowledge Intake）

## 是什么

把一份材料收进本地知识库 `D:\Knowledge`。唯一入口是共用脚本 `D:\Knowledge\_service\intake.py`，它打到本地服务 HTTP 接口（`http://127.0.0.1:8765`）。

**三层分工**：
- 本 Skill：理解你要存什么、存到哪个知识域、是归档还是整理。
- 共用脚本 `intake.py`：调服务接口、传文件和来源、返回回执、查最终结果。
- 本地服务：prepared 路径只保存、登记版本、建检索；仅 compile 路径调用后台解析与编译模型。

## 第一步：判断三种意图（关键，不能混）

| 意图 | 含义 | 参数 | 模型是否参与 |
|---|---|---|---|
| **archive 原样归档** | 成稿/已写好的产物，原样保存，**不让模型重写** | `--intent archive` | 否（0 次调用） |
| **compile 资料整理** | 原始资料，保存原文后**交给模型整理成知识** | `--intent compile` | 是（服务端解析+编译） |
| **prepared 客户端已整理** | 你（客户端）已经读完并整理好，提交「原件+解析稿+成果」三件套，服务只保存登记建检索 | `--intent prepared` | 否（后台 0 次调用） |

判断口诀：
- Excel/PDF/Word/PPT 是文件格式，不代表已经整理成稿。「读一下、整理后入库」必须先解析再 prepared；不能因为文件已存在就 archive。只有明确要求仅保存原件时，二进制 archive 才合适，回报“原件已保存／待解析”，不能说正文已入库可检索。
- 「把我们做好的方案/报告/成稿入库」 → **archive**（成品，原样归档）
- 「读这份材料然后入库」「把这篇资料收进知识库整理」「重新跑企服销售包」 → **客户端先读取和整理，再 prepared**，不是直接上传原件到 compile。
- 「交给知识库后台模型解析/编译」或已明确批准采用后台编译的采集任务 → **compile**。普通“整理”“重跑”“入库”不代表授权后台模型调用。
- 「我读完了这个 PDF，帮我把原件、解析稿、结论一起存好」 → **prepared**（客户端已整理，三件套）

关键区分：**prepared 是客户端已经精读整理过的**（比如你自己在对话里读完 PDF 提炼了结论），服务端**不再调模型重写**，只负责保存三层、登记版本、建检索。这与「compile 交给服务端解析+编译」是两条不同路径。

已经读过的材料复用可核验的解析稿；不要重复调用后台解析。客户端无法读取或没有视觉能力时报告限制，可按真实缺页状态保存部分成果；不得静默回退 compile，也不得用外部模型 API 冒充客户端内置多模态。仅用户要原样存已有成稿时使用 archive，不把摘要当完整解析稿。

## 第二步：资料范围与内容标签（不是两个仓库）

统一存储 `--kb library`（默认，可省略），原件只存一次。按材料讲谁标范围，不是按作者/发布者；AI 和 SaaS 是可同时存在的内容标签，不再是知识域。

| 内容 | 资料范围 | 内容标签 |
|---|---|---|
| 微盟 AI 导购方案 | `--scope weimob` | `--tag AI --tag SaaS --tag 导购` |
| 微盟订单中心 PRD | `--scope weimob` | `--tag SaaS --tag 订单` |
| 迈富时 AI 销售研究 | `--scope external` | `--tag AI --tag 销售` |
| 媒体报道微盟智能体 | `--scope weimob` | `--tag AI`；发布者另记 |
| 微盟与外部厂商对比 | `--scope weimob --scope external` | 按主题多选 |

客户端读懂内容后判断，不因出现某词机械归类；不确定省略 scope，回报待分类，不创建新库。标签可自定义，AI/SaaS 自动统一大小写。prepared、archive、compile 都支持上述参数。范围和标签与可信度、公开权限无关，未获批准不发布。

旧 saas/ai/qifu/whatworth/openai-blog/research-wiki 写入口已停用，不能继续用旧 Skill。新库目录 `D:\Knowledge\content`，历史资料按用户要求移出并清空索引。入库前 CLI 检查分类版本，旧服务会明确报错，不静默丢标签。

检索：`py -3.12 D:/Knowledge/_service/intake.py search "导购" --scope weimob --tag AI`。不加筛选为全库；范围和标签组合为交集，双范围材料在两边均可找到。分类随回执/检索返回，不复制材料。

## 第三步：执行（调脚本，不绕过）

### 内容自检与分层验收

英文材料默认保留英文原件和忠实英文解析稿，知识稿用中文整理；不额外全文翻译，不增加模型或审批流程，archive 成稿仍原样保存。中文表述遵循 **信 > 达 > 雅**：信是忠于原意，不漏条件、不扩大承诺，保留数字、功能状态、适用范围；达是按中文习惯自然表达，让业务含义清楚，不逐词硬译；雅是专业简洁、术语一致，不堆辞藻、不润色成营销话术。产品名、API 标识不硬翻；拿不准的术语或句子保留英文并标疑义，重要结论带原文位置，只有影响业务判断的疑义才请用户确认。不能为流畅替原文下结论；中文分析与推断应与原文含义区分。

提交 prepared 前对照原件复核高风险结论（支持范围、渠道状态、价格、数字、版本），逐条保留页码/章节及原文依据：
- 各渠道分别保留「已开放/即将开放/规划中/未知」和适用时点，不把多渠道汇总成全部已支持。销售材料描述不等于已实测上线。
- 原材料日期必须检查：材料日期 `document_date`、公开发布日期 `published_at`、生效日期 `effective_at`、产品版本 `product_version` 分开填写。按原文精度用 YYYY / YYYY-MM / YYYY-MM-DD（明确时分可用 ISO 时间），不能补造日。封面日期只填 document_date，不当发布日期；入库、采集、文件属性时间均不能代替。`date_evidence` 记录每个日期对应的字段、原文位置及日期原话。找不到时省略日期字段，填 `date_status: unknown` 和 `date_note`（查过哪里、为什么未知）；有材料/发布日期填 known。业务生效日不能单独证明资料年龄。入库来源 JSON 必须带日期或未知说明；未知不拦截保存，不要求用户猜日期。
- 截图数字只描述为截图所载，除非有依据，不称真实经营成果，也不擅自认定为演示数据。
- 正文若列「内容标签」，使用反引号逐个列出，并与提交的结构化标签一致。
- 发现影响能力判断、价格或承诺的不确定项，保存后用 review raise 登记并取得 ID；仅取得回执不能说已登记。待确认事项正文写问题与证据，不预先写“已登记”。普通文字错误直接修正，不交给用户逐字审批。

prepared 提交后、登记确认项后都用 status 回读分层验收。`quality.automatic_check` 是有限一致性检查；`attention`/退出码3表示已保存但需检查，不要盲目重试重复入库。旧回执 `not_checked` 不代表失败也不代表通过。`parse_complete` 是客户端声明；服务不会验证图片全部读过。自动通过不能宣称事实正确。

回报固定区分：①保存了哪些层；②自动检查通过/待处理/未检查；③实际抽查的页码与结论、未查范围、待确认项 ID。没有独立内容核验时直说未核验，不把 done 或空确认列表称作“无冲突”。服务的 content_review=not_verified 不代替客户端报告实际抽查范围。

新客户端或 Skill 更新后首份材料，优先抽查关键图表及支持范围/价格/版本页；日常按风险抽查，不要求每篇再次全文调用模型。发现语义问题先修正文稿，再按版本化 prepared 更新；无需重新解析无变化的原件。不自动扩大为付费后台复核。

### 冲突与不确定项：保存材料，再确认口径

**纯整理纠错例外（不是代用户裁决）**：同一原件、仅修正错字/解析遗漏/总结失真，且原文明确、不涉及不同依据之间取舍时，prepared 可加 `--correction-reason "具体修改及原文页码依据" --base-version N`。先读取当前版本，保留其他内容及未核实标记，不把此参数用于新来源、新产品版本、价格或能力口径争议。把同一原文“即将开放”从误写“已支持”改回，属于整理纠错；判断两个来源哪个才是当前状态，属于业务裁决。

服务核对基准版本和原件内容哈希；仅原件相同、三层齐备、声明解析完整且主题无历史未决项时，省略新建“版本更替待确认”，新版仍保留版本记录和纠错原因。这是客户端纠错声明+机械核验，不是独立语义认证，也不调用 review decide、不伪造 user_confirmed。条件不满足仍走确认；版本过期拒绝提交。已经存在的 review 不自动关闭，其他未决问题不因此被清除。提交后核对 quality.update，只有 version_review_skipped=true 才报告本次免重复确认。

读取/整理时先检索相关知识，对比产品、版本、生效时间与适用范围；记录检索覆盖范围，不声称已检查全库。发现相互矛盾、缺页、依据不足或范围不明时，原件/解析稿照常保存，成果保留各方口径与待核实标记，不先替用户选定答案。prepared 后服务会为解析不完整及同标题更新登记不确定项；不会自动语义扫描全库。客户端发现的其他问题需用 `review raise` 登记。

随后执行 `py -3.12 D:/Knowledge/_service/intake.py review list --kb library`，向入库者展示具体问题、双方原话/位置、范围与建议，取得明确回答再 `review decide`。可以选择采纳一方、按范围并存、新版替代旧版、暂不能确定；暂不能确定继续 pending。只确认具体问题，不把整份材料标成真实。用户没回复时回报“材料已保存，口径待确认”，不自动同意。

命令与 JSON 字段见 [references/confirmation.md](references/confirmation.md)，处理确认或策略时必须读取。所有操作经共用 CLI；prepared/确认不调用后台模型。用户裁决记录中的身份是客户端声明，不是已认证身份。

单次裁决不更新通用策略。确有重复适用价值时，另提 `propose-policy`，展示规则文字和适用范围；用户明确同意推广为规则后才 `policy-state active`，可另行撤销。新材料版本不能套用旧版本裁决。检索的 `review_items` 与 `active_policies` 必须用于回答：披露未决问题，仅在范围匹配时采用已确认结论/策略；它们不改写原始证据。

### 来源依据：入库记录，回答裁决

prepared 提交时尽量准备来源 JSON，用 `--source-metadata-file "<路径>"` 传入。未知字段省略，不根据文件名猜测状态或版本。支持字符串字段：
`source_kind`（repo_wiki/prd/sales_material/commercial_policy/contract/other/unknown）、`publisher`、`document_date`、`published_at`、`effective_at`、`date_status`（known/unknown）、`date_note`、`date_evidence`、`product`、`product_version`、`scope`、`repository`、`commit`、`source_revision`、`lifecycle`、`locator`（原文页码/章节；逐条依据仍写在成果中）。来源不同于解析者；客户端生成的总结不能自称 Repo Wiki，只有实际基于对应代码的来源才能这样标。

日期未知可以正常保存；缺检查、格式混填或缺日期依据会返回提醒，查回执后补信息，不重复投原件。archive/compile 暂无这组结构化参数，明确回报日期尚未结构化，不声称已完整记录；archive 成稿不要为此改写正文。回答时披露原材料时间；价格、接口、模型能力等时效性事实需结合当前来源复核。较旧只提示复核，不自动删除或判无效，方法论和历史案例仍可能有价值。

知识稿 version 是修订号，不是 product_version 或 source_revision。新元数据当前经 prepared 链路保存；旧材料未补录不能假称有权威来源标签。archive/compile 仍可用，但不支持该新增参数。

入库保留各方原件与口径，不因低优先级删除证据。不把保存成功当成冲突核验成功。回答前可用 `py -3.12 D:/Knowledge/_service/intake.py search "<查询>" --kb library` 检索（不调用后台问答模型），必要时继续读命中原文，不能只看摘要就裁决。

回答时先判断问题及适用范围，再择依据：同产品/版本/范围的实际实现问题，有对应 commit 的 Repo Wiki > 已评审 PRD > 销售材料；设计规划优先已评审 PRD；价格权益优先生效商业政策；客户承诺优先适用的已确认合同。范围/版本/状态不明或同级冲突时保留待核实，不能硬选。代码存在不代表已上线。说明采用来源、取舍理由和另一口径，不隐去冲突。优先级不是入库覆盖规则，不触发后台模型调用。

**服务按需自动拉起**：`intake.py` 提交前会探测本地服务（`http://127.0.0.1:8765`），
没跑就自动在后台启动并等就绪。你无需手动起服务；若脚本报「无法启动/未就绪」，
多半是缺 token，去看 `D:\Knowledge\_local\logs\server_auto.log`。

```bash
# 原样归档（成品）
py -3.12 D:/Knowledge/_service/intake.py submit --intent archive --file <路径> --title "<标题>" --kb <kb_id>

# 仅用户明确授权后台解析/编译时使用
py -3.12 D:/Knowledge/_service/intake.py submit --intent compile --file <路径> --kb <kb_id>

# 客户端已整理（三件套：原件+解析稿+成果，后台 0 模型调用）
# 短稿直接传文本；长解析稿/成果用 --extract-file / --wiki-file 从文件读，避免塞满命令行
# 若某页图片读不出，加 --parse-incomplete --missing-pages 2 5（如实声明解析不完整）
py -3.12 D:/Knowledge/_service/intake.py submit --intent prepared --file "<原文件路径>" --title "<标题>" --extract-file "<解析稿文件路径>" --wiki-file "<成果文件路径>" --parser "<客户端解析用的工具或模型>" --kb <kb_id>

# 以下正文/链接同样仅限明确授权后台编译；只有链接不代表已取得正文
py -3.12 D:/Knowledge/_service/intake.py submit --intent compile --text "<正文>" --kb <kb_id>
py -3.12 D:/Knowledge/_service/intake.py submit --intent compile --url "<链接>" --kb <kb_id>
```

## 「读一下 PDF 然后入库」的标准流程

当用户说「读这个 PDF 然后入知识库」，你（客户端）应完成：

1. **客户端读取 PDF**：核对总页数，逐页读取文字并实际查看页面或图片，涵盖图文混排、扫描页、表格、产品截图、流程图；有文字层不代表图片已读取。可以用本地工具提取文字、渲染页面，但必须由当前客户端可用的视觉能力理解图像。小字不清时放大或局部查看，仍不可辨认则标缺失，不能猜测。解析稿按原页序保留文字、表格和图像位置/含义；装饰图可标为装饰，不必扩写。
2. **整理成果**：基于解析稿，写出结论/分析/专题。
3. **准备三件套**：
   - 原件 = 原始 PDF 文件路径
   - 解析稿 = 写到一个临时 .md/.txt 文件（含页码、表格、图片说明、未识别标记）
   - 成果 = 写到一个临时 .md 文件（你的结论）
4. **调 prepared 入库**：用 `--extract-file` / `--wiki-file` 传长稿，`--parser` 如实记录你的解析方式。

Word/PPT 同理：正文提取不能代替对嵌入图片、截图和图表的实际读取；用页码、幻灯片号或章节+图片序号定位。无法获得完整覆盖时显式声明不完整。

Excel：逐个工作表提取非空行列（包括隐藏工作表），保留工作表名、行号/列号、合并范围、数值单位及公式与缓存值的区别。普通单元格可用本地工具提取，不必调用模型；不能把公式缺失缓存当空白或0。检查嵌入图片、图表和其他对象；没有读到的部分显式标记，并用 --parse-incomplete。用原件中的关键行列和数值抽查解析稿。prepared 提交原件、解析稿、含具体表格内容的知识稿，不能只提交文件名或摘要占位。回执 content_status=needs_parse / complete=false / 退出码3 时是待处理，不要重试或报全部完成。

批量重跑：记录逐文件清单（原件路径、主知识域、实际覆盖范围、未识别项、回执、最终状态），逐份完成三件套。保留原件与旧版，不自行删除旧库、改旧回执或将新稿迁入正式目录。先用一份含关键图表的文件核验解析新增内容和 prepared 回执，再继续同批次；回报完成/部分/失败数量。不能仅凭工具调用成功就断言图片已识别，也不能把后台 0 调用说成客户端完全免费。

**关键**：如果某页图片读不出来，解析稿里如实标「第 N 页图片：未识别（待补）」，并在入库命令里加 `--parse-incomplete --missing-pages N`。服务会把「三层保存状态」和「解析完整性」分开记录：三层都存了但解析不完整，返回的 `complete` 仍是 False。**不要**靠正文关键词让服务猜——客户端必须显式声明解析是否完整。

脚本会**轮询到最终结果**（done/failed），不会拿到回执就说完成。查历史回执：

```bash
py -3.12 D:/Knowledge/_service/intake.py status <receipt_id>
```

## 铁律

1. **不要绕过脚本直接写文件或直连服务**——逻辑只存在于服务接口 + 脚本。
2. **三条路径不能混**——成稿 archive；客户端读图整理 prepared；仅明确授权后台处理才 compile。prepared 后台不调模型，客户端自身仍可能消耗额度。
3. **回执不等于完成**——compile 等最终结果；prepared 同时检查 saved_layers、parse_complete、missing_pages。重复提交也检查这些状态。status 的 done 只表示处理结束，不代表解析完整；缺页须如实提示。
4. **失败如实记录**——失败原因从回执的 error 读，不编造成功。
5. **密钥、路径、知识域都在脚本和 config 里**，本 Skill 不重复定义业务逻辑。

## 边界

- 不支持音视频（缺转写/抽帧工具，如实标「待支持」）。
- 资料范围不决定公开权限；统一库默认私有。
- 主题同义识别（「微盟星元」vs「星元智能体」）尚未支持，可能分两篇。
